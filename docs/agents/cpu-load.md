# CPU load

Other sessions and the user share this PC. Parallel test runners and artificial CPU load (busy loops, `stress-ng`, "burners") slow it down, and burners keep running after the session ends.
- Run test runners with at most 2 workers, for example `vitest --maxWorkers=2`, `stryker run --concurrency 2`, `playwright test --workers=2`, `jest --maxWorkers=2`. Pass the limit on the command line; do not change committed config for it. If the committed config already sets a lower limit (such as `workers: 1`, `maxWorkers: 1`, or `fileParallelism: false`), pass no worker flag and no `VITEST_*` variable: they override the config and can make a serial suite run in parallel.
- Only the owner starts burners, with a `!` command. The auto-mode permission classifier denies a burner that an agent starts, so never start one yourself and never work around the denial. Ask the owner. Give the exact start command and the exact stop command. The rules below are the rules for the commands that you give.
- Use at most half of the cores for burners: at most `nproc / 2` burners, one per core, pinned with `taskset -c` to cores `0` to `nproc / 2 - 1`. Pin the code under test to the same cores: a host process with `taskset -c`, a container with `--cpuset-cpus`. The other cores stay free.
- Wrap each burner in `timeout` of at most 30 minutes. For more time, give the owner a new start command. A short timeout stops orphaned burners if the session dies.
- The start command writes the PIDs of the burners to a file in your scratchpad: each Bash call starts a new shell, so `$!` is lost. The stop command kills only the PIDs whose command (`ps -o args= -p <PID>`) is still the burner. Give the owner a check command of the same form to show that none is left. Do not use `pgrep -f` for this check: it also matches the shell that runs it.
- If the problem does not reproduce at this load, ask the owner. Never raise the load by yourself.
