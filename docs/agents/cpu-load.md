# CPU load

Other sessions and the user share this PC. Parallel test runners and artificial CPU load (busy loops, `stress-ng`, "burners") slow it down, and burners keep running after the session ends.
- Run test runners with at most 2 workers, for example `vitest --maxWorkers=2`, `stryker run --concurrency 2`, `playwright test --workers=2`, `jest --maxWorkers=2`. Pass the limit on the command line; do not change committed config for it. If the committed config already sets a lower limit (such as `workers: 1`, `maxWorkers: 1`, or `fileParallelism: false`), pass no worker flag and no `VITEST_*` variable: they override the config and can make a serial suite run in parallel.
- Never start a burner yourself. Only the user starts burners: the auto-mode permission classifier denies them, and you must not work around it. Write the exact burner command that follows the rules below, then ask the user to run it with `!` in your session's terminal. A worker asks through its coordinator, and the user runs the command in the worker's terminal.
- Use at most half of the cores for burners: the command starts at most `nproc / 2` burners, one per core, pinned with `taskset -c` to cores `0` to `nproc / 2 - 1`. Pin the code under test to the same cores: a host process with `taskset -c`, a container with `--cpuset-cpus`. The other cores stay free.
- Wrap each burner in `timeout` of at most 30 minutes. Ask the user for new burners if you need more time. A short timeout stops orphaned burners if your session dies.
- Make the command write the burner PIDs to a file in your scratchpad: each `!` command starts a new shell, so `$!` is lost. Before you finish, give the user a stop command that kills only the PIDs whose command (`ps -o args= -p <PID>`) is still a burner. After the user runs it, check the same way that none of them is still a burner. Do not use `pgrep -f` for this check: it also matches the shell that runs it.
- If the problem does not reproduce at this load, ask the user. Never ask for more load than these rules allow.
