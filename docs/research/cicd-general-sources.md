# General CI/CD guidance sources for a fallback mode

## Question

Which published CI/CD (Continuous Integration and Continuous Delivery) guidance is neutral to language and CI system? A fallback mode of a CI/CD skill can cite it. The skill today covers GitHub Actions for Node/TypeScript only. The fallback gives general advice and writes no files.

Access date for all pages: 2026-11-18. All pages were read on their official sites.

## Short answer

- No single source covers all topics.
- Use DORA (DevOps Research and Assessment) for pipeline stages, CI practice, deployment automation, and low-risk delivery. It has a clear quoting license (CC BY 4.0). [1]
- Use the OWASP (Open Worldwide Application Security Project) Top 10 CI/CD Security Risks for secrets, permissions, fork triggers, and artifact integrity. License: CC BY-SA 4.0. [3][4]
- Use SLSA (Supply-chain Levels for Software Artifacts) v1.2 for provenance, signing, and build isolation. [5][6]
- Use the OpenSSF (Open Source Security Foundation) Concise Guide for secrets, signing, and dependency hygiene. Use the NIST (National Institute of Standards and Technology) SSDF (Secure Software Development Framework) as a high-level anchor. [7][8]
- Treat Scorecard checks and the OpenSSF SCM guide as GitHub-leaning. Cite them for ideas, not as neutral rules. [10][11]
- Gaps: caching, per-event triggers (push, tag, schedule), pinning and lockfiles, deploy approvals and environments. See the gaps section.

## Sources

### DORA capabilities (dora.dev)

- Topics: pipeline stages (continuous integration, continuous delivery, deployment automation, test automation); change approval; trunk-based development; version control; small batches; monitoring; pervasive security. [1]
- Neutrality: The catalog names no CI system and no language. It states goals, for example "Make deploying software a reliable, low-risk process that can be performed on demand at any time." [1]
- License: "All content on this site is licensed by Google LLC under CC BY 4.0, unless otherwise specified." Attribution is required. [1]
- Version and date: the catalog page shows none. Cite the URL and access date. [1]
- Limit: it gives capabilities and outcomes, not concrete settings. It does not cover caching, pinning, or secrets in detail.

### OWASP Top 10 CI/CD Security Risks

- Topics: credential hygiene (CICD-SEC-6); identity and access (SEC-2); pipeline-based access controls (SEC-5); poisoned pipeline execution and fork-triggered runs (SEC-4); dependency chain abuse (SEC-3); artifact integrity (SEC-9); insufficient flow control, such as approvals (SEC-1); logging (SEC-10). [2][3]
- Neutrality: The risk pages use general terms ("pipelines", "source control"). Example quote: "Each pipeline should only have access to the credentials it needs to fulfill its purpose." The pages show no neutrality statement. [3]
- License: CC BY-SA 4.0 (page footer and repository). Share-alike applies to quoted text. [3][4]
- Version and date: the pages show no date. The project roadmap lists a v1.0 release in 2022. [3]
- SEC-4 recommendations: [3]
  - Run unreviewed code on isolated nodes without secrets.
  - Gate runs from forks, for example by manual approval.
  - Protect every branch that can trigger a sensitive pipeline.

### SLSA (slsa.dev), version 1.2 (v1.1 is the older page)

- Topics: provenance and signing; hosted build platform; build isolation; cache poisoning prevention. [5][6]
- Neutrality: The build platform "could be a system of multiple independent rebuilders." GitHub Actions, Google Cloud Build, and Travis CI appear only as examples. The spec has no explicit neutrality statement. [6]
- Key requirements: L1 provenance exists; L2 hosted build and signed provenance; L3 isolated, ephemeral builds and unforgeable provenance. [6]
- License: Community Specification License 1.0. [5]
- Version and date: v1.2, status Approved. No publication date on the page (copyright 2026). [5]
- Limit: it covers builds and supply chain. It does not cover triggers, caching strategy, or deploy approvals. It also has a Source Track. [5]

### OpenSSF Concise Guide for Developing More Secure Software

- Topics: CI security tooling; no secrets in repositories, with detection tools; signing important releases (example tool: cosign); dependency evaluation, monitoring, and updates. [7]
- Neutrality: "All tools or services listed are merely examples." The guide does not explicitly cover pinning or lockfiles. [7]
- License: none named on the page. It says the site is open source and points to lfprojects.org for terms. Check the repository license before long quotes. [7]
- Date: published 2023-06-14. No version number. [7]

### NIST SSDF, SP 800-218 version 1.1

- Topics: high-level practice groups: Prepare the Organization, Protect the Software, Produce Well-Secured Software, Respond to Vulnerabilities. It names practices, not settings. [8][9]
- Neutrality: "No examples or combination of examples are required, and the stated examples are not the only feasible options." [9] The abstract says the practices fit "any SDLC". [8]
- License: the page states none. NIST links a copyrights page; that page returned 404 when fetched. Treat reuse terms as unverified. [8]
- Version and date: v1.1, final, February 2022. The project page lists no newer version. [8][9]

### OpenSSF Scorecard checks

- Topics: Token-Permissions (least-privilege tokens), Pinned-Dependencies, Dangerous-Workflow, Signed-Releases, Branch-Protection, CI-Tests, Dependency-Update-Tool, SBOM (Software Bill of Materials), SAST (Static Application Security Testing). [10]
- Neutrality: weak. The page marks Token-Permissions, Pinned-Dependencies, CI-Tests, Signed-Releases, Packaging, and SAST as GitHub-only. Dangerous-Workflow targets GitHub Actions. Code-Review supports GitHub, GitLab, Prow, and Gerrit. [10]
- License, version, date: not stated on the page. Verify the repository license before quoting. [10]
- Use: as a list of ideas. The ideas (pin by hash, least-privilege token) apply to any CI, but the check text does not.

### OpenSSF Source Code Management Best Practices

- Topics: branch protection; required reviews and status checks; CI/CD token permissions, approvals, and action restrictions; secret scanning; commit signing. It does not cover pinning or releases. [11]
- Neutrality: partial. It covers GitHub and GitLab and marks each item per platform. [11]
- License: not named; links to lfprojects.org terms. [11]
- Date: 2023-08-29. No version. [11]

### CIS (Center for Internet Security) Software Supply Chain Security Guide

- Topics: it targets teams that ship software updates through automated pipelines. The landing page does not list the sections. I did not read the guide itself, so I claim no topic coverage. [12]
- Neutrality and license: not stated on the page. [12]
