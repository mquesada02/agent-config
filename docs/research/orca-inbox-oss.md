# Open-source projects for the inbox and coordinator problems

Ticket 754 of map 752 (request 750). Date of reading: 2026-11-17. Builds on `docs/research/agent-workflow-comparison.md` (issue 723); it does not repeat that file.

Marks: **FACT** = taken from the source named. **INFERENCE** = our reading. Star counts, `pushed_at`, licence (SPDX) and release data come from the GitHub API (`gh api repos/OWNER/REPO` and `.../releases/latest`) on 2026-11-17, unless a line says otherwise. Doc quotes were read through a fetch tool that summarises pages with a small model, so they are near-verbatim, not byte-exact. Orca facts come from the Orca findings file of ticket 753 (`docs/research/orca-inbox-orca.md` on branch `research/orca-inbox-orca`, Orca app version 1.4.261), cited as "Orca §x.y". ## 1. Question

Which public projects solve: (a) one inbox for questions from many agent sessions; (b) a central coordinator over several repos; (c) routing a worker question to whoever can answer it; (d) approvals that need no person; (e) local notifications? For each: what it does, how it is built, maturity, licence, comparison with Orca. Which ideas can this setup reuse?

## 2. Short answer

1. No project does all five; the problems split across different projects.
2. Inbox (a): cmux "Feed" is the best design reference. Its hooks park an agent request until the human answers in a UI or a desktop notification. amux, HumanLayer, Happy and Nimbalyst are next.
3. Central coordinator over repos (b): only Gas Town (a Mayor over many "rigs") documents it. Ruflo and Agor claim it; their pages give little detail.
4. Routing (c): only Gas Town documents an agent-first chain with a human last (severity, timeouts, re-escalation). mcp_agent_mail has a message bus but no escalation. Claude Code agent teams are one team per session, no nesting.
5. No-person approval (d) has three mechanisms: static rules, a second model (Claude Code auto mode, Codex auto-review, OpenHands analyzer) and deny-guards (cc-safety-net).
6. Notifications (e): Claude Code `Notification` hook plus ntfy or a chat bridge with Approve/Deny buttons (Channels permission relay, Lucarne, claude-ntfy-hook).
7. Licence risks: cmux (GPL), Claude Squad and CloudCLI (AGPL), amux (Commons Clause), Agor (BSL) and the Rust mcp_agent_mail (custom rider) are not permissive.
8. A search sweep (section 3.5) found newer projects close to Orca: Novadeck (one inbox plus agent messaging by handle; GPL-3.0), Squadra (recorded owner decisions with options and a recommendation; MIT), CAO (supervisor and workers on tmux; Apache-2.0) and Hermes IDE (worktree IDE with an attention inbox; BSL). Most other hits have under 100 stars.
9. Reusable ideas are in section 5; each needs the owner's decision.

Details, with sources:

- **cmux** (https://github.com/manaflow-ai/cmux; docs/feed.md, docs/agent-hooks.md in the repo). FACT: a native macOS terminal app (Swift, libghostty). An agent hook calls `cmux hooks feed`, which sends the verb `feed.push` over a unix socket. A FeedCoordinator parks the hook on a semaphore keyed by request id, for up to 120 seconds. The human answers in the Feed sidebar, a TUI (`cmux feed tui`) or a macOS notification with inline actions. Items are permission requests (Once, Always, All tools, Bypass, Deny), ExitPlanMode and AskUserQuestion. Storage is an in-memory ring buffer plus a JSONL audit file. Hooks exist for Claude and about 19 other agents. `cmux ssh` and `cmux mosh-tmux` relay hooks from remote hosts. Not read: the multi-machine-sessions and phone-push docs. vs Orca: Orca has a durable mailbox per Run with ask, reply and decision gates (Orca §3.2, 3.4, 3.5) and alerts a person by bell, sound, unread dot and phone push when an agent goes idle (Orca §3.7), but it has no queue of "waiting for the owner" items across Runs (Orca §6 item 1); that queue is what the Feed gives. cmux shows no coordinator and worker messaging in the pages read. GPL limits reuse of its code.
- **HumanLayer** (https://github.com/humanlayer/humanlayer). FACT: README says it "runs coding agents (Claude Code, Codex, OpenCode, Pi) on your machines and lets your team steer them from one place". Bun monorepo, Hono API, Postgres synced with Electric, one daemon per host. The Claude plugin README says: "From the web app you can reply, stop a turn, answer permission prompts and comment on task files". Self-host is "a reference, not a supported install". The latest release is 2025-12 while pushes are daily. INFERENCE: it pivoted from an approvals SDK to team steering. vs Orca: both steer many agents from one place. HumanLayer syncs through a server database across hosts and lets a person answer permission prompts from the web app; Orca keeps mail in one local SQLite database (Orca §3.3, §6 item 8), reaches other servers by `send --on` (Orca §3.6), and has no answer path from the phone to a gate (Orca §6 item 3).
- **Happy** (https://github.com/slopus/happy; docs/backend-architecture.md). FACT: a CLI wraps Claude or Codex and mirrors the session to an E2E-encrypted phone app. Fastify and Socket.IO relay with Postgres, Redis and S3; machine daemon per host; a Cloudflare Worker sends push through APNs and FCM. The README does not describe approving a permission from the phone; docs/permission-resolution.md exists, not read. vs Orca: Orca's mobile app (beta) gets push when an agent finishes and has an Agents tab (Orca §3.7) but no answer path to a gate (Orca §6 item 3); Happy covers the phone side only and has no orchestration layer in the pages read.
- **Nimbalyst** (https://github.com/nimbalyst/nimbalyst). FACT: Electron workspace for Claude Code, Codex and OpenCode with parallel worktree sessions; an iOS companion app shows which agents wait for input, sends push, and takes a reply by text or voice. The sync server is a separate project. It succeeds Crystal (`stravu/crystal`, last push 2026-02-26). vs Orca: the same shape (worktree sessions in one app; Orca §3.8, 3.9) plus a phone that pushes when an agent waits and takes a reply; Orca's phone push mirrors desktop notifications (Orca §3.7) with no reply path (Orca §6 item 3). No coordinator mailbox is shown in the README read.
- **amux** (https://github.com/mixpeek/amux; docs/self-hosting.md). FACT: one Rust binary and SQLite (axum on port 8824, event journal, SSE), tmux workers by default. README: "Watch, steer and approve from the iPhone and iPad app, the Mac app or the browser". It has a shared task board and agent-to-agent messages ("agents ask, hand off and unblock peers"); the mechanism was not read beyond the README. Created 2026-02-18; not OSI open source. Another repo, `andyrewlee/amux`, is unrelated. vs Orca: the nearest in function. Orca has ask, reply, send and check per Run (Orca §3.2, 3.4) over a local SQLite database (Orca §3.3); amux has messages plus a task board over SQLite, tmux workers and a phone approval path that Orca lacks (Orca §6 item 3). amux is not a worktree IDE, and its licence is not OSI.
- **Vibe Kanban**. FACT: `crates/executors/src/approvals.rs` defines `ExecutorApprovalService` with `create_tool_approval` and `create_question_approval`, so tool and question approvals are first class. It has an MCP crate and relay crates (INFERENCE: remote access). A worktree per task, like Orca. vs Orca: Orca also has worktrees (Orca §3.8) and models a question as `ask` to a coordinator and as a decision gate (Orca §3.4, 3.5); Vibe Kanban's approvals go to the person in its UI, and no coordinator mailbox was found.
- **CCManager**. FACT: a TUI over worktrees and projects, with status hooks that run shell commands (docs/status-hooks.md) and an experimental AI auto-approval verifier (`src/services/autoApprovalVerifier.ts`). INFERENCE: it detects "waiting" by screen state. vs Orca: Orca lists agent state per workspace in `worktree ps` (Orca §3.8) and notifies on working to idle (Orca §3.7), so it has the status list; the Orca file names no AI auto-approval feature.
- **Claude Squad**. FACT: Go, tmux, worktrees; it hashes pane output to detect change and auto-presses Enter on the trust prompt; an AutoYes mode exists. No inbox. vs Orca: Orca covers worktrees and terminals with read, send and wait (Orca §3.8) and adds the mailbox (Orca §3.2); Claude Squad is the smaller tool.
- **CloudCLI** (siteboon/claudecodeui). A web UI with web-push modules (INFERENCE: not shown to carry approvals). vs Orca: it is a remote web front end for sessions; Orca's remote access is its mobile app with push and an Agents tab (Orca §3.7), and CloudCLI has no mailbox or Run in the pages read.
- **Emdash** (generalaction/emdash). An IDE-style peer with worktrees, ticket import and remote SSH machines; the README shows no inbox. vs Orca: Orca has the same worktrees (Orca §3.8) plus a mailbox (Orca §3.3) and reaches other machines with `--on` (Orca §3.6).
- **Omnara** (omnara-ai/omnara). Now a hosted agent platform, no longer the mobile approval app; only partly relevant. vs Orca: a hosted service, where Orca's mail is local (Orca §3.3, §6 item 8); a different category.
- **LangChain Agent Inbox** (archived). FACT: a Next.js app that fetches LangGraph `interrupt` objects and sends human responses back; actions are accept, edit, respond, ignore. It is tied to LangGraph, not to CLI agents. Useful as a UX pattern. vs Orca: Orca's `ask` takes `--options` and `reply` answers it (Orca §3.4), and gates carry options (Orca §3.5), so the same shape exists; what Orca lacks is a view of those items (Orca §6 item 1), and `inbox` only lists mail in 200-character previews (Orca §3.3).
- **AgentAPI** (archived). FACT: README says it is "deprecated and no longer maintained". An HTTP wrapper over a PTY; a building block only. vs Orca: Orca already has `terminal read`, `send` and `wait` (Orca §3.8), so AgentAPI adds nothing it lacks.
- **Claude Code Channels** (https://code.claude.com/docs/en/channels). FACT: "A channel is an MCP server that pushes events into your running Claude Code session". Channel servers that declare the permission relay capability "can forward these prompts to you so you can approve or deny remotely"; "Anyone who can reply through the channel can approve or deny tool use in your session". Research preview; one session each. vs Orca: a transport between a chat and one session. Orca's push comes from agent state changes (Orca §3.7, INFERENCE there) and its mail is agent to coordinator (Orca §3.2); a channel could carry the human answer that Orca's phone lacks (Orca §6 item 3).

Details, with sources:

- **Gas Town** (https://github.com/gastownhall/gastown; README; docs/design/escalation.md). FACT: the Town is the parent workspace, a Mayor is "the primary AI coordinator" (a Claude Code instance), and each "rig" wraps one git repo with its agents. The Mayor "coordinates work across rigs". README: "Agents that hit blockers escalate via `gt escalate`, which creates tracked beads"; "Escalations route through Deacon -> Mayor -> Overseer based on severity." Design doc: "Each tier can resolve OR forward. The chain is tracked via bead comments." MEDIUM = bead and mail to the Mayor; HIGH = also email to the human; CRITICAL = also SMS. `stale_threshold` defaults to 4 h, `gt escalate stale` raises severity, `max_reescalations` defaults to 2, and an ack stops re-escalation. Human channels default to empty. Go CLI `gt`, hooks, mailboxes, beads as state. INFERENCE: the only documented match for both (b) and (c). The mechanism (severity, timeout, ack) is reusable as an idea; the code is MIT. vs Orca: Orca has the parts of the chain but not the rules. Messages carry priority `normal`, `high` or `urgent` but `check` cannot filter by it (Orca §3.2, §6 item 2); an `escalation` message means a worker stopped (Orca §3.4); nested coordinators receive group mail in a child Run mailbox (Orca §3.6) and workers nest to depth 4 (Orca §3.12); a folder workspace can hold the repos of one group (Orca §3.9), like a rig set. Orca documents no timeout, re-escalation or email and SMS step.
- **mcp_agent_mail** (README, raw.githubusercontent.com/Dicklesworthstone/mcp_agent_mail/main/README.md). FACT: an MCP server with `send_message(..., thread_id, ack_required)`, `fetch_inbox`, `acknowledge_message`; Git archive, SQLite index, web UI and TUI. Contact policies `open`, `auto`, `contacts_only`, `block_all`. "Overseer messages bypass normal contact policies". "An agent working in Project A is invisible to agents in Project B" unless they share a `project_key` or have contact links. It carries messages and acks; nothing routes a question or escalates on timeout. The Python repo is deprecated; the Rust successor has a custom licence rider. Closest standalone analogue to `orca orchestration` ask, send and check; no worktrees or terminals. vs Orca: the same primitives as an Orca Run (`send`, `check`, `reply`; Orca §3.2, 3.4), but addressing differs: Orca uses `run:<id>`, `dispatch:<id>` and `@` groups (Orca §3.6), mcp_agent_mail uses a `project_key` and contact policies. Cross-Run send in Orca is UNTESTED (Orca §3.6, §6 item 5). Orca adds worktrees and terminals (Orca §3.8). The Rust licence rider limits reuse.
- **Beads** (gastownhall/beads). A task and issue graph for agents, the state layer of Gas Town (API description; docs not read). vs Orca: Orca keeps tasks, Runs and messages in one local SQLite database (Orca §3.3) and has gates for blocking questions (Orca §3.5); Beads is a work-item store, not a message bus.
- **Claude Code agent teams and cross-session messaging** (https://code.claude.com/docs/en/agent-teams; .../cross-session-messaging.md). FACT: "One session acts as the team lead"; the mailbox is "a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; "Teammate permission prompts appear in the lead session"; "One team per session ... You can't ... share a team across sessions"; "No nested teams"; "Lead is fixed". Cross-session: `ListAgents` and `SendMessage` over a local Unix socket; "A message ... can't approve anything"; Claude is told not to ask another session for an action that was denied in its own session and to "route that work back to you". INFERENCE: it has no reply-correlated ask and no multi-coordinator structure. vs Orca: Orca §3.13 says the same of `SendMessage` and `ListAgents`: messages "enqueue and drain at the receiver's next tool round", a session in another permission mode holds them for approval, and there is "no durable inbox and no Run"; Orca has both (Orca §3.1, 3.3).
- **Ruflo** (README only). FACT: claims queen-led hierarchy, federation across machines with mTLS and ed25519, and "AgentBBS rooms". INFERENCE: marketing-heavy, with no verifiable ask or escalation detail. The earlier research (723) found its own audit calls headline claims unsubstantiated. Treat as unverified. vs Orca: Orca documents peer mail to a paired server (`send --on`, capability `orchestration.federation.v1`; Orca §3.6); Ruflo's federation claims cannot be compared beyond the README.
- **Agor** (README). FACT: a web workspace; "Every piece of work is a git branch with its own working directory"; it "exposes itself over MCP, so agents can fork, spawn, schedule, and report"; Slack and GitHub gateways. No escalation chain or multi-repo coordination described. BSL 1.1, source-available. vs Orca: the same worktree-centred idea (Orca §3.8, 3.9). Orca adds a CLI message bus with ask, reply and gates (Orca §3.2, 3.4, 3.5); Agor's agents report through MCP and its gateways go to Slack and GitHub.
- **Libraries** (OpenAI Agents SDK, LangGraph supervisor, AG2, CrewAI). FACT: handoffs "stay within a single run" (OpenAI); a supervisor coordinates specialist agents and can nest (LangGraph); AG2 v1 has typed channels where `consulting` is "one question, one reply, auto-closing" and a pluggable `hitl_hook` for a person (AG2 README); CrewAI delegation "is now disabled by default". INFERENCE: in-process, per run, with no terminals or persistent sessions. AG2 `consulting` and `hitl_hook` are the nearest vocabulary for ask/reply with a human fallback. vs Orca: these run inside one process and one run, with no terminals or persistent mailbox. Orca's mail survives a session because it is stored in SQLite and resumed with `run-use` (Orca §3.1, 3.3, §6 item 4).
- **A2A** (https://a2a-protocol.org/latest/topics/life-of-a-task/). FACT: "When something is ambiguous, the agent returns an `input-required` state to ask the client for clarification"; the client answers in a follow-up. The protocol does not say who answers. INFERENCE: a standard shape for ask and reply. vs Orca: `input-required` plus a follow-up answer matches Orca's `ask` and `reply` (Orca §3.4). Orca's bus is local with optional federation (Orca §3.3, 3.6), and A2A is a wire protocol, so Orca could map onto it (INFERENCE). ACP is archived.
- **OpenHands** (README). FACT: one container and Agent Server per conversation; the canvas "can connect to multiple Agent Servers". No agent-to-agent routing described. vs Orca: a sandbox and server per conversation; Orca runs real terminals in worktrees (Orca §3.8), and the OpenHands README has no mailbox, ask or gate to compare with Orca §3.2 to 3.5.
- **ccswarm** (API readme). FACT: a pipeline with a quorum of reviewer agents; "it does not resolve dissent". No question routing. vs Orca: a staged pipeline with a reviewer quorum; Orca has the message types `merge_ready` and `decision_gate` and dispatches per Run (Orca §3.2, 3.5) but no quorum.

- **Claude Code auto mode** (https://code.claude.com/docs/en/permission-modes). FACT: "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content". "If the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting." With no verdict, "Claude Code denies the action rather than run it unreviewed". `dontAsk` "auto-denies every tool call that would otherwise prompt you". Calls needing approval are denied unless an allow rule, hook, `canUseTool` callback or `--permission-prompt-tool` approves them. An allow rule or hook cannot approve recognised `rm` critical-path removals or reads from a network path. vs Orca: the Orca file names no auto-approval feature. In Orca a question waits for a coordinator `reply` or a gate resolution (Orca §3.4, 3.5); auto mode runs inside each Claude Code session, below Orca, so the two layers do not overlap.
- **Claude Code hooks** (https://code.claude.com/docs/en/hooks; first 100k of 294k characters read). FACT: `PreToolUse` returns `permissionDecision` (allow, deny, ask, defer); `PermissionRequest` returns `decision.behavior` (allow, deny); "a `PreToolUse` call stays blocked even if you return "allow"" after exit 2. Notification types include `permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`. INFERENCE: the hook point where an Orca-side policy or inbox could attach. vs Orca: Orca §3.13 notes that an `asyncRewake` background hook "wakes the model on exit code 2" (INFERENCE, not tested there); the Orca file lists no Orca-side policy hook.
- **Codex** (https://learn.chatgpt.com/docs/agent-approvals-security). FACT: sandbox modes read-only, workspace-write, danger-full-access; policy `on-request`, `never`, `granular`; `approvals_reviewer = "auto_review"` routes requests "through a reviewer agent"; "Auto-review uses extra model calls". The Codex `notify` option was not verified. vs Orca: Orca starts Codex as a provider in automations (Orca §3.10) and runs it in terminals (Orca §3.8); the approval policy and the auto-review stay inside Codex, and Orca does not set them (the Orca file lists no such feature).
- **Gemini CLI** (https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/reference/policy-engine.md). FACT: "evaluates all rules to find the highest-priority rule that matches the tool call"; decisions allow, deny, ask_user; "In non-interactive mode, this is treated as `deny`". Tiers Admin, User, Workspace, Default. The cleanest rules-only (no model) approver. vs Orca: same layer as the Codex item, inside the agent CLI; Orca's own routing is by message type and address (Orca §3.2, 3.6), not by tool-call rules.
- **OpenHands** (https://docs.openhands.dev/sdk/guides/security). FACT: under `ConfirmRisky(threshold=HIGH)`, MEDIUM and LOW actions "run automatically"; `conversation.execute_tool()` "bypasses the analyzer and confirmation policy". vs Orca: a risk score gates actions inside the agent; Orca has no risk level, only message priority (Orca §3.2), and a worker's question goes to its coordinator (Orca §3.4).
- **cc-safety-net**. FACT: "parses what the command does"; it "does not contain processes, set filesystem permissions, or watch network egress". INFERENCE: a deny-guard, not an approver. vs Orca: it works per agent CLI, below Orca; the Orca file names no deny-guard, so it would sit next to Orca without overlap (INFERENCE).
- **claude-code-hooks-mastery** (disler; table above). FACT: a demo of all hook events, with PermissionRequest auto-allow for read-only operations and a text-to-speech Notification hook. vs Orca: a code example for the hook layer, not a product; nothing in Orca §3 overlaps it.
- **CCManager, Claude Squad**: see 3.1 (auto-approval by AI verifier or Enter press), with their "vs Orca" lines.

### 3.4 Local notifications

- **Claude Code `Notification` hook**. FACT (hooks doc): a Notification hook can return `terminalSequence` (OSC 777) for a desktop alert. vs Orca: Orca already fires a system notification, sound and workspace chip when an agent goes idle, with a header bell (Orca §3.7); the hook adds alerts for events such as `permission_prompt` that Orca's idle trigger may not cover (Orca §3.7 INFERENCE).
- **ntfy** (binwiederhier/ntfy; 35613 stars; v2.38.1 on 2026-11-16; Apache-2.0). FACT: "send push notifications to your phone or desktop via scripts from any computer"; self-hostable HTTP pub-sub. vs Orca: Orca has its own phone push through its mobile app (beta, pairing code, optional relay; Orca §3.7); ntfy is a generic transport that a script could call for events Orca does not push.
- **claude-ntfy-hook** (nickknissen; 6 stars; pushed 2026-02-26; MIT). FACT: a PreToolUse hook sends an ntfy push with Allow and Deny buttons for tools on the `ask` list, and "exits with code 0 to allow the call or code 2 to block it". Tiny, but the exact pattern: blocking hook plus phone buttons. vs Orca: Orca's phone push has no answer buttons (Orca §6 item 3); this is the answer path it lacks, for one agent.

## 4. Comparison with Orca

Orca facts are from the Orca findings file (ticket 753, Orca app version 1.4.261); the reading of them against the projects is INFERENCE.

What Orca has (FACT, Orca file):
- A durable mailbox per Run, in one local SQLite database; one coordinator can hold several Runs and be woken by mail from all of them (Orca §3.1, 3.2, 3.3).
- `ask`, `reply`, `escalation` (a worker stopped without `worker_done`) and decision gates that block a task (Orca §3.2, 3.4, 3.5); message priority `normal`, `high`, `urgent`, but `check` has no priority filter (Orca §3.2, §6 item 2).
- `orchestration inbox` lists every mailbox on the local Orca, in 200-character previews, without ranking (Orca §3.3).
- Alerts: a bell, a sound, an unread dot and phone push (mobile beta) when an agent goes idle (Orca §3.7); worktrees, terminal read, send and wait, and per-workspace comment and status (Orca §3.8); a folder workspace that can hold several repos (Orca §3.9); automations with a precheck (Orca §3.10); peer mail to a paired server with `send --on` (Orca §3.6).

What Orca lacks (FACT, Orca §6): an owner queue ranked across Runs (item 1); a priority filter (item 2); an answer from the phone to a gate (item 3); a coordinator that works while no live session exists (item 4); tested cross-Run send (item 5). Cross-Run send and the use of `check --peek --wait` with `Monitor` are UNTESTED there.

Where the projects fill those gaps (INFERENCE):
- Owner queue: cmux Feed, Novadeck Inbox, Hermes IDE attention inbox (3.1, 3.5). All three sit on the human side; none documents an agent-to-agent bus like Orca's.
- Answer from the phone: amux, Nimbalyst, HumanLayer, Happy (partly), Channels permission relay, Lucarne, claude-ntfy-hook (3.1, 3.4).
- Escalation rules with timeouts: only Gas Town (3.2). Orca has the message types and priorities but documents no timeout or re-escalation.
- Central session over several repos: Gas Town (Mayor), Shura (Program Manager). Orca can hold the topology as a folder workspace plus Runs (Orca §3.9, 3.1), but a work group of about 20 repos was not tested (Orca §3.9, UNTESTED).
- Bus: Orca's is richer than mcp_agent_mail (worktrees, terminals, gates) and than Claude Code `SendMessage` (no durable inbox, no Run; Orca §3.13). CAO and Orchvia are the closest peers; amux is the closest in function.
- Auto-approval: the Orca file names none; all items in 3.3 work inside the agent CLI, below Orca.

Conclusion (INFERENCE): nothing found replaces the Orca bus. The missing parts are the owner queue, the phone answer path and the escalation rules; the projects above supply designs for each, and none supplies all three.

## 5. Options for the owner

Each option is a candidate for a decision ticket. Costs are INFERENCE.

1. **Copy the Gas Town escalation model** (severity levels, per-tier resolve or forward, stale timeout, re-escalation cap, ack) as a written protocol over the existing Orca bus. Cost: a protocol spec and coordinator rules; the central session must track timers. No code reuse needed.
2. **Build an inbox on hooks, as cmux Feed does**: a hook parks the request, a local UI or desktop notification answers, an audit file records it. Cost: a local daemon plus hooks per agent; the cmux code is GPL, so copy the design only.
3. **Adopt an existing tool as the inbox** (HumanLayer, amux or Nimbalyst). Cost: a second system next to Orca, a licence check (amux and Agor are not open source), and a server to run for HumanLayer.
4. **Add an auto-approval layer in front of the inbox**: static rules (Claude Code allow rules, the Gemini TOML style) first, an auto-mode classifier second, a person last. Cost: rule upkeep; the classifier can pause after 3 blocks in a row or 20 in total, so the person stays the fallback; hard limits (critical-path `rm`) cannot be auto-approved.
5. **Notifications through ntfy or a chat bridge with Approve and Deny buttons** (claude-ntfy-hook pattern, Lucarne, Channels permission relay). Cost: a sender allowlist is mandatory ("Anyone who can reply through the channel can approve or deny tool use"); a push can approve a risky call from a phone; the owner decides which actions may be approved remotely.
6. **Do nothing new**: keep one coordinator per project group and the current ask and reply. Cost: the owner load stays.
